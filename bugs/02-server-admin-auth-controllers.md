# Server: admin and auth controllers

Scanned: 2 files, 3297 lines. Found: 5 critical, 7 high, 9 medium, 9 low.

## server/controllers/adminController.js

- [LOW] L48-59 (LIKELY) `getAnalytics` (and `getAllPurchases` L484-490, `getPurchaseStats` L522-528, `getActivationReport` L575-590) build the "today", "week" and "month" boundaries with `new Date(y, m, d)` and `setHours(0,0,0,0)` in the server's timezone, and L203 groups the trend by `toISOString()` (UTC day). Impact: when the server runs in UTC (the code is deployed on Vercel) an admin in India sees "today" start at 05:30 IST, so purchases made between 00:00 and 05:30 IST are counted in the previous day. Fix: compute the day boundaries and the `dayKey` in the Asia/Kolkata timezone.
- [MEDIUM] L181 (LIKELY) `getAnalytics` loads `Purchase.find(purchaseQuery)` with no `paymentStatus` filter and sums `packagePrice` of every row into `totalRevenue`, `packagesSold` and `purchaseTrend`; `getPurchaseStats` does the same at L534-540. Impact: any Purchase whose `paymentStatus` is `pending`, `failed` or `refunded` (the schema default is `pending`) is counted as revenue and as a sale, so the admin sees inflated revenue and order counts. Fix: add `paymentStatus: "completed"` to the purchase query in both functions.
- [LOW] L836 (CONFIRMED) `rejectKyc` assigns `user.kycVerified`, and `updateUserStatus` (L871, L882) and `approveKyc` (L1051) do the same, but the User schema has no `kycVerified` field, so Mongoose silently drops the value. Impact: the flag is never stored, so any code or client that reads `user.kycVerified` always gets `undefined` even after KYC approval. Fix: add `kycVerified: { type: Boolean, default: false }` to the User schema, or remove these assignments and rely on `status` and `kycApprovedDate`.
- [MEDIUM] L838 (CONFIRMED) `rejectKyc` always sets `user.status = "free"`, even when the user's status was `active` because they bought a package (and `activationDate` is left set). Impact: a paying, activated user whose KYC document is rejected is downgraded to a free user in the genealogy and in every admin list, while `isActive` and `activationDate` still say active. Fix: on KYC rejection set `status` to `"active"` when `user.activationDate` is set, and to `"free"` only otherwise.
- [LOW] L1372 (CONFIRMED) `getUserDashboardData` returns `profilePhoto: user.profilePhoto`, but the User schema stores the photo in `imageUrl` and has no `profilePhoto` field. Impact: the admin view of a user's dashboard never shows the user's photo because the value is always `undefined`. Fix: return `user.imageUrl`.
- [MEDIUM] L1613-1624 (CONFIRMED) `deleteUser` only checks `Purchase` and direct referrals before `User.findByIdAndDelete(id)`; it does not check `SuperPackagePurchase`, `Wallet`, `RechargeWallet`, `Payout`, the coin wallet or KYC records. Impact: an admin can delete a user who bought only a super package, or who has a wallet balance or a pending payout, which leaves money records pointing at a user that no longer exists and makes the balance unrecoverable. Fix: also refuse deletion when the user has a super package purchase, a non-zero Wallet or RechargeWallet balance, or any Payout row.
- [LOW] L1775 (CONFIRMED) `addMoneyToWallet` takes `userId` from `req.body` and ignores `req.params.userId` from the route `/users/:userId/wallet/add`; `deductMoneyFromWallet` (L1854), `addMoneyToSmartWallet` (L1935) and `deductMoneyFromSmartWallet` (L2000) do the same. Impact: if the body and the URL name different users, the user in the body is credited or debited while logs and the URL show another user, and a request with no `userId` in the body fails even though the URL has one. Fix: read `userId` from `req.params.userId` and reject the request when a body `userId` is present and different.
- [LOW] L1778 (CONFIRMED) `addMoneyToWallet` validates with `!amount || amount <= 0` on the raw value and then uses `parseFloat(amount)`; the same check is at L1857, L1938 and L2003. Impact: `amount: "abc"` passes the check, becomes `NaN` and ends in a 500 error instead of a 400; `amount: "Infinity"` passes and saves a balance of `Infinity`; `amount: "50abc"` is silently treated as 50; and there is no rounding to 2 decimals for the regular wallet. Fix: convert with `Number(amount)` first, then require `Number.isFinite(n) && n > 0`, and round to 2 decimal places.
- [CRITICAL] L1808-1828 (CONFIRMED) `addMoneyToWallet` reads the wallet with `Wallet.findOne`, changes `balance`, `totalEarned` and `activeIncome`/`passiveIncome` in memory and calls `save()`, which writes the absolute values. Impact: if a commission credit, a withdrawal or a second admin request changes the same wallet between the read and the save, that other change is overwritten, so money is lost or created; a double-click by the admin stores two `fund_credit` transactions but can raise the balance only once. Fix: use one atomic `Wallet.findOneAndUpdate({ userId }, { $inc: { balance, totalEarned, activeIncome }, $push: { transactions } }, { upsert: true, new: true })`.
- [LOW] L1838 (CONFIRMED) `addMoneyToWallet` builds the response `transactionId` with a second `Date.now()` call instead of reusing the `reference` stored at L1825; the same happens at L1919 vs L1905, L1984 vs L1970 and L2058 vs L2044. Impact: the transaction id shown to the admin can differ from the `reference` saved in the wallet by one or more milliseconds, so the id cannot be used to find the transaction later. Fix: build the reference once in a variable and use it both in the transaction and in the response.
- [CRITICAL] L1877-1908 (CONFIRMED) `deductMoneyFromWallet` checks `wallet.balance < numericAmount` and then subtracts in memory and calls `save()`. Impact: two deduct requests sent together both pass the balance check and both store a `withdrawal` transaction, but the balance is reduced only once; a commission credited between the read and the save is erased. Fix: use an atomic `Wallet.findOneAndUpdate({ userId, balance: { $gte: numericAmount } }, { $inc: { balance: -numericAmount, totalWithdrawn: numericAmount }, $push: { transactions } })` and return "Insufficient wallet balance" when it matches nothing.
- [CRITICAL] L1957-1974 (CONFIRMED) `addMoneyToSmartWallet` reads the RechargeWallet with `getOrCreateWallet`, sets `smartWallet.balance` and `totalAdded` to new absolute values and calls `save()`. Impact: a recharge payment, a refund or a top-up approval that changes the Smart Wallet between the read and the save is overwritten, so the user gets back money already spent or loses a refund. Fix: apply the credit with an atomic `$inc` on `balance` and `totalAdded` plus `$push` of the transaction.
- [CRITICAL] L2022-2048 (CONFIRMED) `deductMoneyFromSmartWallet` checks `smartWallet.balance < numericAmount` and then writes the new absolute balance with `save()`. Impact: if the user pays for a recharge or an order at the same moment, both operations pass their balance checks and one write overwrites the other, so the same money is spent twice or the admin deduction is lost. Fix: use an atomic `RechargeWallet.findOneAndUpdate({ userId, balance: { $gte: numericAmount } }, { $inc: { balance: -numericAmount, totalSpent: numericAmount }, $push: { transactions } })`.
- [LOW] L2129-2144 (CONFIRMED) `getUserTransactionHistory` uses the query strings `page` and `limit` without validation in `(page - 1) * limit`, `slice(skip, skip + parseInt(limit))` and `Math.ceil(totalTransactions / limit)`. Impact: `limit=0` returns no rows and a total page count of `Infinity` (sent as `null`), `limit=abc` returns no rows and `NaN`, and `page=0` or a negative page makes `skip` negative so `slice` returns rows from the end of the list. Fix: parse both with `parseInt`, then clamp `page` to at least 1 and `limit` to a range such as 1 to 200.

## server/controllers/authController.js

- [MEDIUM] L42 (CONFIRMED) `uploadProfilePhoto` is `multer({ storage })` with memory storage and no `limits.fileSize` and no `fileFilter`. Impact: any logged-in user can post a very large file or a non-image file to `/api/auth/profile-photo`; the whole file is held in memory, which can exhaust the server process, and a non-image only fails later inside `compressProfilePhoto` with a 500. Fix: add `limits: { fileSize: 5 * 1024 * 1024 }` and a `fileFilter` that accepts only `image/jpeg`, `image/png` and `image/webp`.
- [CRITICAL] L155-159 (CONFIRMED) `signup` reads `role` from `req.body` and keeps it when it equals `"admin"`, then passes it to `User.create` at L261. Impact: anyone can send `POST /api/auth/signup` with `"role": "admin"` and get an admin account; a normal `/api/auth/login` then returns a token that passes the `admin` middleware, giving full access to every `/api/admin` route, including adding money to wallets. Fix: remove `role` from the request handling and always create the user with `role: "user"`.
- [MEDIUM] L208 (CONFIRMED) `signup` hashes `password` before any length check, so the schema rule `minlength: 6` on `password` is tested against the 60-character bcrypt hash and never against the real password. Impact: a signup with a 1-character password such as `"a"` is accepted, and a non-string password (a number or an object) makes `bcrypt.hash` throw and returns a 500. Fix: before hashing, require `typeof password === "string"` and `password.length >= 6`, and return 400 otherwise.
- [HIGH] L245 (CONFIRMED) `signup` creates the user without checking that the mobile number passed OTP verification; `verifyOtp` is imported but never called, and `/api/auth/verify-otp` stores no "verified" state that `signup` could check. Impact: a script can call `/api/auth/signup` directly with made-up mobile numbers and emails and create unlimited accounts; each one credits 1000 coins to itself (L271) and 100 coins to the chosen sponsor (L292), and coins can be requested as a rupee withdrawal in `coinsController`. Fix: have `verify-otp` record the verified mobile (for example a short-lived signed token or a database row) and make `signup` reject the request unless that record exists for the same mobile.
- [LOW] L251 (CONFIRMED) `signup` stores `sponsorName` exactly as sent by the client, although it loads the real sponsor in `sponsorUser` at L243. Impact: a signup request can pair a valid `sponsorId` with any text as `sponsorName`, so the user's record and every screen that shows `sponsorName` display a name that does not belong to the sponsor. Fix: set `sponsorName` to `` `${sponsorUser.firstName} ${sponsorUser.lastName}` `` from the database record.
- [MEDIUM] L371 (CONFIRMED) `login` passes `req.body.userId` straight into `User.findOne({ userId })` with no type check, and `checkMobileExists` (L118), `adminSendOtp` (L429), `adminLoginWithOtp` (L482), `signup` (L183) and `lookupSponsorById` (L1051) do the same with their body fields; the app has no query sanitizer. Impact: a JSON body such as `{"userId": {"$gt": ""}, "password": "123456"}` or `{"sponsorId": {"$regex": "^A"}}` runs a Mongo operator query, which lets a caller try one password against users selected by a pattern and read user records without knowing any id. Fix: reject the request with 400 unless each of these fields is a string (`typeof value === "string"`).
- [HIGH] L384-394 (CONFIRMED) `login` checks only that the user exists and the password matches; it never checks `user.status === "blocked"` or `user.isActive`, and the `protect` middleware does not check them either. Impact: a user whom the admin blocked with `deactivateUser` or `updateUserStatus` can still log in and keep using every user feature, including withdrawals. Fix: return 403 from `login` when `user.status === "blocked"`, and add the same check in `protect` so existing tokens stop working.
- [MEDIUM] L391 (CONFIRMED) `login` has no attempt limit: the handler keeps no failure counter and the route `POST /api/auth/login` in `server/routes/auth.js` L83 has no rate limiter (the `authRateLimit` limiter exists but is not used). Impact: an attacker can try unlimited passwords against any user id or mobile number, and the different messages at L387 and L393 confirm which ids and mobiles exist. Fix: apply `authRateLimit` to the login route, add a per-account failed-attempt lockout, and return one generic message for both failures.
- [MEDIUM] L397-401 (CONFIRMED) `login` issues a normal 7-day token to users whose `role` is `admin`, and the `admin` middleware only checks the role stored in the database, not the `isAdmin` claim that `adminLoginWithOtp` adds. Impact: the email OTP step for admin login is optional, because an admin password alone (which can be brute-forced, see L391) gives a token that works on every `/api/admin` route for 7 days instead of 8 hours. Fix: make `login` refuse users with `role === "admin"`, or make the `admin` middleware require `decoded.isAdmin === true`.
- [LOW] L429 (CONFIRMED) `adminSendOtp` looks up `User.findOne({ email })` with the email exactly as typed, and `adminLoginWithOtp` does the same at L482, while the schema stores emails in lower case. Impact: an admin who types the email with a capital letter or a trailing space gets "Admin account not found" and cannot log in. Fix: use `email.trim().toLowerCase()` for the lookup and for the OTP key in both handlers, as `sendForgotPasswordOtp` already does.
- [HIGH] L555-571 (CONFIRMED) `toggleMotivationQuoteStatus` in this file is mounted at `PATCH /api/auth/motivation-quotes/:id/toggle` (`server/routes/auth.js` L121) with no `protect` and no `admin` middleware. Impact: anyone on the internet, without logging in, can hide or show any motivation quote; the ids are public through `GET /api/auth/motivation-quotes/active`. Fix: delete this handler and its route, because the protected copy already exists at `/api/admin/motivation-quotes/:id/toggle`.
- [HIGH] L574-583 (CONFIRMED) `deleteMotivationQuote` in this file is mounted at `DELETE /api/auth/motivation-quotes/:id` (`server/routes/auth.js` L123) with no `protect` and no `admin` middleware. Impact: anyone, without logging in, can permanently delete every motivation quote by reading the ids from `GET /api/auth/motivation-quotes/active`. Fix: delete this handler and its route, because the protected copy already exists at `/api/admin/motivation-quotes/:id`.
- [MEDIUM] L689 (CONFIRMED) `resetPasswordWithOtp` hashes `newPassword` with no length or type check, after the OTP has already been consumed by `verifyEmailOtp` at L671. Impact: a password of 1 character is accepted, and a non-string `newPassword` makes `bcrypt.hash` throw a 500 after the OTP is deleted, so the user must request a new OTP. Fix: validate `typeof newPassword === "string" && newPassword.length >= 6` before calling `verifyEmailOtp`.
- [HIGH] L704-718 (CONFIRMED) `debugOtpStore` returns `getOtpStoreStatus()` and is mounted at `GET /api/auth/debug/otp-store` (`server/routes/auth.js` L108) with no authentication. Impact: anyone can list the email address, attempt count and expiry time of every user who has a password-reset OTP pending, which exposes user emails and tells an attacker exactly which accounts have a live OTP to guess. Fix: remove the handler and the route, or protect the route with `protect` and `admin`.
- [HIGH] L1061-1071 (CONFIRMED) `lookupSponsorById` returns the `email`, `mobile`, `status` and `imageUrl` of the user whose `userId` is sent, and the route `POST /api/auth/lookup-sponsor-by-id` has no authentication and no rate limit. Impact: anyone can walk through user ids and collect the email address and mobile number of every user. Fix: return only `userId`, `firstName` and `lastName` (what the signup form needs), and add a rate limiter to the route.
- [HIGH] L1117-1127 (CONFIRMED) `lookupSponsorByMobile` returns the `userId`, `email`, `status` and `imageUrl` of the user who owns a mobile number, and the route `POST /api/auth/lookup-sponsor-by-mobile` has no authentication and no rate limit. Impact: anyone can test mobile numbers and get the matching user's login id and email address, which is then usable for the unlimited login attempts described at L391. Fix: return only `userId`, `firstName` and `lastName`, and add a rate limiter to the route.
