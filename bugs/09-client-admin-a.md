## client/src/components/Admin/AdminActivationTracker.jsx

- [MEDIUM] L13 (CONFIRMED) `formatDateInput` builds the date string with `date.toISOString()`, which is the UTC date, so `defaultEnd`, the Reset button and the `max` of the End Date input all use the UTC day instead of the admin's local day. Impact: in India between 00:00 and 05:30 the default range ends on yesterday, today's activations and registrations are missing from the report, and the End Date input does not allow picking today. Fix: build the string from the local date parts (`getFullYear()`, `getMonth() + 1`, `getDate()`) instead of `toISOString()`.

## client/src/components/Admin/AdminAnalytics.jsx

- [MEDIUM] L20 (CONFIRMED) `formatDateInput` uses `date.toISOString()`, so the "Today", "Last 7 Days" and "Last 30 Days" presets and the `max` of the End Date input are computed from the UTC date, not the local date. Impact: in India between 00:00 and 05:30 the "Today" preset sends yesterday as both `startDate` and `endDate`, so the dashboard shows yesterday's numbers and today cannot be selected. Fix: format the date from local parts (`getFullYear()`, `getMonth() + 1`, `getDate()`).
- [MEDIUM] L68-70 (CONFIRMED) The `thisMonth` preset creates `start` as local midnight on the 1st (`new Date(end.getFullYear(), end.getMonth(), 1)`) and then passes it through `formatDateInput`, which converts to UTC; in any timezone ahead of UTC (India) local midnight on the 1st is still the last day of the previous month in UTC. Impact: "This Month" always sends the last day of the previous month as `startDate`, so revenue, orders and new-user counts for the month include one extra day from the previous month. Fix: format the start date from local date parts so it is `YYYY-MM-01`.
- [LOW] L326-328 (CONFIRMED) `avgOrdersPerDay` divides `purchaseStats.totalPurchases` by `purchaseTrend.length`, and the server's `trend` array only contains days that had at least one purchase, not every day in the period. Impact: for a 30 day range with sales on 3 days, "Orders Per Day" shows the average per selling day (10 times too high) while the helper text says "Based on selected period". Fix: divide by `analytics.period.days`.
- [LOW] L330-336 (CONFIRMED) `periodSummary` shows "Entire history" only when `analytics.period` is null, but the server always returns a `period` object and for the "All Time" preset its `start` is `new Date(0)`. Impact: with "All Time" selected the header shows "1/1/1970 – <today> (20000+ days)" instead of "Entire history". Fix: show "Entire history" when `analytics.period.timeRange === "all"` and `analytics.period.customRange` is false.

## client/src/components/Admin/AdminDTHAnalysis.jsx

- [MEDIUM] L74 (LIKELY) `fetchAllDTHRecharges` requests `limit=1000` from the all-recharges endpoint (mobile and DTH together, newest first) and filters `rechargeType === 'dth'` in the browser to compute every statistic card. Impact: once the total number of recharges of all types in the selected range is above 1000, older DTH recharges are left out and Total Transactions, Total Revenue, Total Commission and Success Rate are all too low. Fix: add a `rechargeType` filter to the server stats and list endpoints and compute DTH statistics on the server.
- [MEDIUM] L151 (CONFIRMED) `fetchRecharges` (and `fetchStats` L54, `fetchAllDTHRecharges` L76, `getTotalDTHCount` L184) send `filters.endDate` as a bare `YYYY-MM-DD` string, and the server uses `createdAt <= new Date(endDate)`, which is 00:00 UTC of that day. Impact: recharges made on the selected end date are excluded (after 05:30 India time), so choosing the same start and end date shows almost nothing. Fix: send the end of the day (for example `endDate + "T23:59:59.999"` converted to ISO) or make the server extend the end date to the end of the day.
- [HIGH] L153-168 (CONFIRMED) `fetchRecharges` asks the server for one page of 20 recharges of all types and then keeps only rows with `rechargeType === 'dth'`, while `getTotalDTHCount` (L190) returns `pagination.totalRecords`, which is the count of all recharges, not DTH ones. Impact: each page shows only the DTH rows that happen to fall inside that mixed page (often none, giving "No DTH recharge transactions found" although DTH recharges exist), and the page count and "total" text are those of all recharges. Fix: filter by `rechargeType=dth` on the server and use the server's pagination for that filtered query.
- [HIGH] L199-201 (CONFIRMED) `handleFilterChange` always returns `{ ...prev, [key]: value, page: 1 }`, so when it is called with `key === 'page'` by the Previous and Next buttons (L600, L607) the new page number is immediately overwritten with 1. Impact: the Next button never leaves page 1, so only the first page of transactions can ever be viewed, edited or deleted. Fix: do not reset `page` when `key === 'page'`, as `AdminRechargeAnalysis.handleFilterChange` already does.
- [MEDIUM] L225 (CONFIRMED) `handleSaveEdit` always sends the whole `editForm`, including unchanged `amount` and `operator`, and the server's `updateRecharge` recalculates and overwrites `adminCommission`, `adminCommissionPercentage`, `userCommission` and `userCommissionPercentage` whenever `amount` or `operator` is present in the body. Impact: values typed into the four commission inputs are always discarded, and editing only the status or notes silently rewrites the stored commission of an old recharge with the current rate. Fix: send only the fields the admin actually changed, and leave out `amount` and `operator` when they are unchanged.
