# Server: payment, payout, wallet and coin controllers

Scanned: 7 files, 4581 lines. Found: 11 critical, 10 high, 12 medium, 5 low.

## server/controllers/superPackageController.js

- [CRITICAL] L52-77 (CONFIRMED) `distributeSuperPackageCommissions` loads each sponsor `wallet` with `Wallet.findOne`, adds to `wallet.balance` and `wallet.totalEarned` in memory and calls `wallet.save()`, which writes the new totals with `$set`, not `$inc`. Impact: when two writers touch the same sponsor wallet at the same time (two admins verifying two purchases that share an upline, or a commission landing while a payout approval is saving the same wallet), the later save overwrites the earlier one and a commission or a deduction is silently lost. Fix: credit with one atomic `Wallet.updateOne({ userId }, { $inc: { balance, totalEarned }, $push: { transactions } }, { upsert: true })` per sponsor.
- [HIGH] L62-63 (LIKELY) `distributeSuperPackageCommissions` increases only `wallet.balance` and `wallet.totalEarned`; it never increases `wallet.activeIncome` (level 1) or `wallet.passiveIncome` (levels 2-120), which the regular package path in `referralService.distributeCommissions` does. Impact: `requestPayout` limits a withdrawal to `activeIncome` or `passiveIncome`, so super package commission sits in `balance` but cannot be withdrawn; a user whose only earnings are super package commissions gets "You are not eligible for payout". Fix: add `commissionLevel.amount` to `activeIncome` when `sponsor.level === 1` and to `passiveIncome` otherwise, in the same atomic update.
- [MEDIUM] L203-205 (CONFIRMED) `updateUserMLMLevel` sets `user.mlmLevel = "Active Member"` whenever the value is anything other than "Active Member". Impact: a user who already holds a higher rank ("Team Leader", "Assistant Manager", "Manager", "Zonal Head", "National Head Promoter") is downgraded to "Active Member" when their super package payment is verified. Fix: only change `mlmLevel` when it is currently "Free".
- [MEDIUM] L473-505 (CONFIRMED) `purchaseSuperPackage` uploads `req.files.paymentProof` to Cloudinary with `resource_type: "auto"` after checking only `file.size`; `file.mimetype` and the file content are never checked. Impact: any logged-in user can store arbitrary files (HTML, video, executables, up to 10MB each) in the company Cloudinary account under `super-package-payments`. Fix: accept only image mimetypes (and verify the content, for example by passing the buffer through the existing `compressPaymentProof` helper) and upload with `resource_type: "image"`.
- [CRITICAL] L843-867 (CONFIRMED) `updateSuperPackagePaymentVerificationStatus` reads the verification with `findById`, checks `verification.status !== "pending"` in memory and then saves, so the check and the write are not atomic. Impact: two requests for the same `verificationId` arriving together (a double click on Verify, or two admins) both pass the check, and each creates a `SuperPackagePurchase` and runs `distributeSuperPackageCommissions`, so the whole commission pool is paid twice for one payment. Fix: claim the record with `SuperPackagePaymentVerification.findOneAndUpdate({ _id: verificationId, status: "pending" }, { $set: { status, ... } })` and stop if it returns null.
- [HIGH] L965-968 (CONFIRMED) In `updateSuperPackagePaymentVerificationStatus` the `catch` around purchase creation and commission distribution only logs the error, after `verification.status` was already saved as "verified" on L867. Impact: if `SuperPackagePurchase.create`, the user lookup or `distributeSuperPackageCommissions` throws (for example a wallet validation error half way up the sponsor chain), the admin still gets "Payment verification verified successfully", the buyer may have no purchase or stay inactive, only some sponsors are paid, and the verification can never be processed again because it is no longer "pending". Fix: run the purchase and commission steps in a MongoDB transaction with the status change, or revert the status and return an error when they fail, and make distribution idempotent per purchase.

## server/controllers/coinsController.js

- [MEDIUM] L31-37 (LIKELY) `grantActivationBonus` only checks `wallet.activationBonusGranted`; it never checks that the caller's account is activated (`req.user.status`). Impact: any newly registered free user can call `POST /api/coins/activation-bonus` and receive the 1000 coin activation bonus without buying a package. Fix: return 403 unless `req.user.status` is "active" or "kyc_verified".
- [MEDIUM] L38-45 (CONFIRMED) `grantActivationBonus` credits the coins with `wallet.addCoins(...)` (first save) and only afterwards sets `wallet.activationBonusGranted = true` (second save). Impact: a second request that reads the wallet between the two saves still sees `activationBonusGranted === false` and credits another 1000 coins. Fix: claim the flag first with `CoinWallet.findOneAndUpdate({ userId, activationBonusGranted: false }, { $set: { activationBonusGranted: true }, $inc: { balance: 1000, totalEarned: 1000 }, $push: { transactions } })` and return 400 when nothing matched.
- [MEDIUM] L93-99 (CONFIRMED) `requestCoinWithdrawal` compares only the single request's `withdrawalAmount` with `maximumCoins`, although the limit and its message say "per day". Impact: once one request is approved the user can immediately submit another 100000 coin request, so the Rs 1000 per day cap is not enforced. Fix: sum the user's `WithdrawalRequest.coins` created today with status pending, approved or completed and reject when the sum plus the new amount exceeds `maximumCoins`.
- [MEDIUM] L129-174 (CONFIRMED) `requestCoinWithdrawal` checks for an existing pending `WithdrawalRequest` with `findOne` and then creates a new one, with no unique constraint. Impact: two requests sent together both find no pending request and both are saved, so the user ends up with two pending withdrawals against the same coins. Fix: add a partial unique index on `{ userId }` where `status` is "pending" and handle the duplicate key error.
- [LOW] L327 (CONFIRMED) `adjustUserCoins` calls `CoinWallet.getOrCreateWallet(targetUserId)` without checking that the user exists. Impact: a mistyped `targetUserId` creates a coin wallet for a user that does not exist and the coins are credited there, while the admin sees success. Fix: look up `User.findOne({ userId: targetUserId })` first and return 404 when it is missing.
- [LOW] L328-348 (CONFIRMED) In `adjustUserCoins`, when `parseInt(amount, 10)` gives `NaN` (for example `amount: "abc"`) neither the credit nor the debit branch runs, but the handler still answers success. Impact: the admin sees "Adjusted NaN coins for user ..." although nothing changed. Fix: return 400 when `numericAmount` is `NaN` or 0.
- [CRITICAL] L490-501 (CONFIRMED) The approve branch of `processWithdrawal` only sets the wallet transaction `status` to "completed"; it does not reduce `targetWallet.balance` and does not update the matching `WithdrawalRequest`. Impact: withdrawals created by `requestCoinWithdrawal` do not deduct coins at request time, so approving one through `POST /api/coins/admin/withdrawals/process` marks it paid while the user keeps all the coins, and the `WithdrawalRequest` stays "pending" forever, which blocks the user from making any new request. Fix: remove this endpoint or make it call the same logic as `approveWithdrawalRequest` (deduct coins and update the `WithdrawalRequest`).
- [CRITICAL] L510-512 (CONFIRMED) The reject branch of `processWithdrawal` adds `refundAmount` to `targetWallet.balance` and subtracts it from `targetWallet.totalWithdrawn`, but `requestCoinWithdrawal` never deducted those coins. Impact: rejecting a pending withdrawal through this endpoint gives the user free coins equal to the requested amount whenever `totalWithdrawn` is at least that amount; otherwise `totalWithdrawn` goes negative, the save fails schema validation (`min: 0`) and the request can never be rejected here. Fix: do not refund anything on reject; only mark the transaction and the `WithdrawalRequest` as rejected.
- [HIGH] L575-581 (CONFIRMED) `getWithdrawalRequests` loads users with `User.find({ userId: { $in: userIds } })` without a field selection and puts the whole user document into each request's `userId` field. Impact: the response contains every requesting user's `password` hash and all other private fields. Fix: add `.select("userId firstName lastName email mobile")`.
- [HIGH] L614-634 (CONFIRMED) `approveWithdrawalRequest` checks `withdrawalRequest.status !== "pending"` on a document read earlier and then saves, so the check is not atomic. Impact: two approve requests arriving together both pass, and when the second one loads the wallet after the first has saved, `amountToDeduct` is taken from the user's coin balance twice for one withdrawal. Fix: claim the request with `WithdrawalRequest.findOneAndUpdate({ _id: requestId, status: "pending" }, { $set: { status: "approved", ... } })` and deduct coins with a conditional `$inc`.
- [CRITICAL] L630-649 (CONFIRMED) `approveWithdrawalRequest` saves `withdrawalRequest.status = "approved"` before it checks that the wallet transaction exists (L642) and that `wallet.balance >= amountToDeduct` (L647), and it does not undo the status when those checks fail. Impact: if the user spent the coins after requesting (coins are not held at request time), the admin gets "Insufficient wallet balance" but the request is now "approved" with nothing deducted; `completeWithdrawalRequest` then accepts it and the user is paid in rupees while keeping the coins. Fix: do the wallet checks and the deduction first (or in one transaction) and only then set the status to "approved".

## server/controllers/payoutController.js

- [HIGH] L201-214 (CONFIRMED) In `requestPayout` the `withdrawableAmount` chain tests `activeIncome > 0` first, so the third branch (`activeIncome > 0 && passiveIncome > 0 && isEligibleForPassiveIncome`, "both") can never run; the same dead branch is in `checkPayoutEligibility` at L79-92. Impact: a user who qualifies for passive income and has, for example, `activeIncome` 50 and `passiveIncome` 10000 gets `withdrawableAmount` 50, which is below the Rs 200 minimum, so they cannot withdraw anything until active income reaches 200, and can never withdraw passive income while any active income remains. Fix: test the "both" case first and set `withdrawableAmount` to `activeIncome + passiveIncome` (capped at the wallet balance) when the user is eligible for passive income.
- [MEDIUM] L258-287 (CONFIRMED) `requestPayout` checks for a pending payout with `Payout.findOne` and then creates a new `Payout`; nothing makes the pair atomic. Impact: two requests submitted together (double click on Withdraw) both find no pending payout and both are saved, so the user has two pending payouts for the same balance. Fix: add a partial unique index on `{ userId }` for `status: "pending"` and return 400 on the duplicate key error.
- [MEDIUM] L344-361 (CONFIRMED) `getTDSHistory` filters only on `userId` and `tds > 0`, with no `status` filter. Impact: pending and rejected payout requests are listed as TDS deductions and are summed into `summary.totalTDS`, so the user is shown TDS that was never deducted. Fix: add `status: { $in: ["approved", "completed"] }` to the three queries.
- [HIGH] L442 (CONFIRMED) `updatePayoutStatus` never validates `status` from the request body before it changes money; the value is only checked by the schema enum when `payout.save()` runs at L775, after the wallet was already saved at L762. Impact: sending a missing or misspelled status (for example `"complete"`) for a payout that is "approved" or "completed" runs the reversal block, credits `payout.amount` back to the wallet, then `payout.save()` fails validation and the payout stays "completed"; every repeat credits the wallet again. Fix: return 400 at the top unless `status` is one of "pending", "approved", "rejected", "completed".
- [CRITICAL] L444-457 (CONFIRMED) `updatePayoutStatus` decides whether to deduct by comparing `payout.status` read with `findById`, and writes the new status only at L775 after all wallet or fund changes. Impact: two approve requests for the same payout arriving together both see "pending"; both push withdrawal transactions, and for fund and special income payouts `funds.deductFunds` or `specialIncome[...] -= payout.amount` can run twice, so the user is charged twice for one payout. Fix: first claim the payout with `Payout.findOneAndUpdate({ _id: payoutId, status: "pending" }, { $set: { status } })` and only continue when it returns a document.
- [CRITICAL] L692-763 (CONFIRMED) The reversal block of `updatePayoutStatus` does not look at `payout.withdrawalType`; it always runs `wallet.balance += payout.amount`. For payouts with `withdrawalType` "fund" or "special_income" the approval deducted from the `Funds` or `SpecialIncome` document and never reduced `wallet.balance`. Impact: approving a fund or special income withdrawal and then changing it to "rejected" or "pending" creates `payout.amount` rupees of withdrawable balance in the main wallet, while the fund or special income is not restored. Fix: in the reversal, branch on `payout.withdrawalType` and restore `funds[payout.fundType]` or `specialIncome[payout.incomeType]` instead of the wallet balance for those types.

## server/controllers/walletTopUpController.js

- [HIGH] L67-71 (CONFIRMED) `submitWalletTopUp` only rejects a `transactionId` when the same user already has a pending top-up with it, and the `WalletTopUp` schema has no unique index on `transactionId`. Impact: after a top-up is approved, the same user (or any other user) can submit the same bank transaction ID and screenshot again, and nothing flags the duplicate, so one real payment can be credited to recharge wallets more than once. Fix: reject when any `WalletTopUp` with that `transactionId` and status "pending" or "approved" exists, and add a unique index on `transactionId`.
- [CRITICAL] L387-433 (CONFIRMED) `approveWalletTopUp` checks `topUp.status !== "pending"` on a document read with `findById`, then credits the recharge wallet by loading it, changing `rechargeWallet.balance` in memory and calling `save()`. Impact: two approve requests for the same top-up arriving together both pass the status check and the amount can be credited twice; the read-then-save of `balance` also overwrites a recharge payment or transfer made by the user at the same moment. Fix: claim the top-up with `WalletTopUp.findOneAndUpdate({ _id: id, status: "pending" }, { $set: { status: "approved", ... } })` and credit with `RechargeWallet.updateOne({ userId }, { $inc: { balance: amountToAdd, totalAdded: amountToAdd }, $push: { transactions } })`.
- [MEDIUM] L404-433 (CONFIRMED) `approveWalletTopUp` saves `topUp.status = "approved"` before crediting the recharge wallet and does not revert it when the credit fails. Impact: if `RechargeWallet.getOrCreateWallet` or `rechargeWallet.save()` throws, the admin gets a 500, the top-up is permanently "approved" with no money credited, and it cannot be approved again or deleted. Fix: do both writes in a transaction, or set the status back to "pending" in the `catch` when the credit did not happen.
- [LOW] L596-597 (CONFIRMED) `deleteWalletTopUp` builds `publicId` from only the last URL segment, but the proof was uploaded with `folder: "wallet-topup-proofs"`, so the real public id is `wallet-topup-proofs/<name>`. Impact: `cloudinary.uploader.destroy(publicId)` never matches and payment proof images of deleted top-ups stay in Cloudinary.
