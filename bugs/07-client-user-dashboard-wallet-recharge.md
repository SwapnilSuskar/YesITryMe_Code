## client/src/components/User/Dashboard.jsx

- [MEDIUM] L95 (CONFIRMED) The `totalWithdrawn` memo sums `payoutHistory`, but `GET /api/payout/history` (`getPayoutHistory` in `server/controllers/payoutController.js`) returns only the 10 newest payouts. Impact: for any user with more than 10 payout requests the "Withdrawn" card and the "Total Income" card (which adds `totalWithdrawn` at L100) are too low. Fix: have the server return the total of approved and completed payouts (or all payouts) and use that value instead of summing a 10-row list.
- [LOW] L204-206 (CONFIRMED) The `fetchTeamIncome` effect calls `setTeamIncome(0)` whenever `referralTree.directReferrals` is empty, and it runs after `fetchDashboardData` has already set `teamIncome` from `commissionData.data.passiveIncome`. Impact: a user with no direct referrals whose wallet has passive income (for example added by an admin with `incomeType: "passive"`) sees "Passive Income ₹0", and the "Wallet" and "Total Income" cards are too low by that amount. Fix: remove the early `setTeamIncome(0)` branch and always use `passiveIncome` from the commission summary.
- [MEDIUM] L405-407 (CONFIRMED) `fetchDownlineStats` reads `data.uniqueSuccessfulDownline` but never reads `data.uniqueIndirectSuccessfulDownline`, so `setUniqueIndirectSuccessfulDownline` is never called and the state stays 0. Impact: "Indirect Package Buyers" and "Total Package Buyers" (L1331 and L1336) always fall back to `indirectBuyers + indirectSuperPackageBuyers`, which counts a person twice when they bought both a package and a super package. Fix: add `if (data.uniqueIndirectSuccessfulDownline !== undefined) setUniqueIndirectSuccessfulDownline(data.uniqueIndirectSuccessfulDownline);`.
- [MEDIUM] L543-546 (LIKELY) `fetchMLMLevel` calls `setUser({ ...user, mlmLevel })` on every successful response, which creates a new `user` object, and the main load effect at L111-128 and six other effects depend on `[user, token]`. Impact: about one second after every dashboard load all dashboard requests are sent a second time and the page falls back to the loading skeleton again; the new level is also not written to `localStorage`. Fix: call `setUser` only when `data.data.mlmLevel !== user.mlmLevel`, and make the fetch effects depend on `user?.userId` instead of the whole `user` object.
- [MEDIUM] L717-718 (CONFIRMED) `combinedDirectData` and `combinedIndirectData` add `downlineStats` and `superPackageDownlineStats` by array index, but the two lists have separate period selectors (`downlinePeriod` and `superPackageDownlinePeriod`) and so can have different lengths and start dates. Impact: with "Regular Packages Period" on 7 days and "Super Packages Period" on Month, index 0 is 6 days ago in one list and 29 days ago in the other, so the bars add counts from different days and super package days beyond the regular length are dropped. Fix: merge the two lists by `item.date`, or use one shared period selector.
- [MEDIUM] L752 (CONFIRMED) `downlineChart` uses `chartData.last7Days` as its labels, and those labels are built from `leadsStats` (always 7 days), while `downlineStats` has 1, 15, 30 or 365 entries when the period is not 7 days. Impact: after choosing "1 Day", "15 Days", "Month" or "All Time" the package buyers chart shows the wrong dates under the bars and cannot show more than 7 days. Fix: build the labels for this chart from `downlineStats.map(item => item.date)`.
- [MEDIUM] L803-808 (CONFIRMED) In `earningsData` the `alltime` case sets `days = 365`, and `fetchEarningsData` (L436) loads only the newest 1000 wallet transactions of every type. Impact: the card titled "All Time Earning Breakdown" leaves out every commission older than 365 days and every commission beyond the newest 1000 wallet transactions, so the Active, Passive and Total figures are too low for long-standing users. Fix: for `alltime` sum all transactions without a date window (or take lifetime totals from the server) and page through all transactions.

## client/src/components/User/WalletTransactions.jsx

- [HIGH] L77 (CONFIRMED) The `creditedTransactions` filter in `fetchWalletTransactions` includes the types `withdrawal` and `payout_received`, and `totalEarned` (L855-857) sums every completed row of that list. The server stores a withdrawal as a negative amount and also adds a positive `payout_received` row for the net amount (`updatePayoutStatus` in `server/controllers/payoutController.js`). Impact: after an approved payout "Total Earned" is wrong, for example a user who earned ₹10,000 and withdrew ₹5,000 sees ₹9,400 (10,000 − 5,000 + 4,400), and the "Credited Amount" list shows the withdrawal as "₹-5,000". Fix: compute `totalEarned` only from earning types (`commission`, `bonus`, `leadership`, `royalty`, `reward`, `fund_credit`, `shop_cashback`) or use `walletData.totalEarned`, and remove `withdrawal` from the credited list.
- [LOW] L100 (CONFIRMED) `fetchRechargeWalletData` asks for `limit=500`, but `getRechargeWalletTransactions` on the server caps `limit` at 200 and the client never requests page 2. Impact: a user with more than 200 smart wallet transactions does not see older top-ups, transfers and admin adjustments, and the "Top-Ups" count is too low. Fix: request further pages until `totalPages` is reached, or raise the server cap to match.
- [HIGH] L261 (CONFIRMED) `fetchRechargeHistory` reads `response.data.totalPages`, but `GET /api/recharge/history` returns the page count as `data.pagination.total`, so `rechargeTotalPages` is always 1 and the check `page <= rechargeTotalPages` at L1743 stops `fetchRechargeHistory` from ever loading page 2 or later. Impact: only the 10 newest recharges are ever loaded, so for a user with more than 10 recharges the "Recharges", "Success", "Failed" and "Spent" cards are wrong and older recharges appear only as rows rebuilt from wallet payments. Fix: read `response.data.pagination.total`, load the full history (or all pages) before merging, and stop `fetchRechargeWalletData` (L103-104) from overwriting `rechargeTotalPages` and `rechargePage`.
- [MEDIUM] L358 (CONFIRMED) In `getAllRechargeTransactions` the pattern `/\+91\s*(\d{10})|(\d{10})/` takes only the first 10 digits of the number in the wallet payment description, but a DTH subscriber ID has 10 to 12 digits. Impact: for a DTH recharge with an 11 or 12 digit subscriber ID the wallet row never matches its history row (`ht.mobileNumber === txn.mobileNumber` at L454 is false), so the same recharge is listed twice, the "Recharges" count is too high, and the extra row shows a cut-off ID as "+91 …" with operator "N/A". Fix: match the wallet row to the recharge by `txn.rechargeId` (the server stores it on the transaction) instead of parsing the description.
- [MEDIUM] L398 (CONFIRMED) For a wallet `recharge_payment` row with no matching history row the status is set to `txn.status || 'success'`, and the wallet transaction status is always `completed`; `recharge_refund` rows are removed by the filter at L329. Impact: a recharge older than the 10 loaded history rows that failed and was refunded is shown as a "completed" payment with no refund, so the user thinks the money was spent. Fix: resolve the real status from the recharge record (by `txn.rechargeId`) and show refund rows, or mark payments that have a matching `recharge_refund` as refunded.
- [LOW] L730 (CONFIRMED) Every virtual row in `virtualFundTransactions` and `virtualSpecialIncomeTransactions` (L730 to L846) is created with `createdAt: new Date()`. Impact: in the "Credited Funds" tab every fund and special income credit is shown with the current date and time, which changes on each visit, instead of the date the admin added it. Fix: do not show a date for these summary rows, or load the real `fund_credit` and `special_income_credit` transactions and use their `createdAt`.
- [MEDIUM] L860-862 (CONFIRMED) `totalWithdrawn` and the payout tab totals at L1761, L1771 and L1781 are computed from `payoutHistory`, which holds at most the 10 newest payouts because `GET /api/payout/history` is limited to 10 rows. Impact: for a user with more than 10 payouts "Total Withdrawn", "Total Requests", "Total Requested" and "Net Received" are too low and older payouts can never be viewed. Fix: add paging and server-side totals to the payout history endpoint and use them here.

## client/src/components/User/Payout.jsx

- [HIGH] L189 (CONFIRMED) `fetchSuperPackageCommissions` stores `response.data.data.balance` as the Super Package commission balance, but `getSuperPackageCommissionSummary` returns `wallet.balance`, the balance of the whole main wallet, in that field. Impact: the "Super Package Commissions" amount (L500, L641, L725) repeats the full wallet balance, `hasSuperPackageCommissions` (L366) shows "Eligible for Withdrawal" and opens the request form for any user whose wallet is above ₹0 even when the server will refuse, and the client limit at L265 allows amounts the server rejects. Fix: show the Super Package figure from a real Super Package balance returned by the server, and do not use `balance > 0` from this endpoint as an eligibility signal.
- [HIGH] L300-311 (CONFIRMED) For `withdrawalSource === 'superPackages'` `handlePayout` posts to `API_ENDPOINTS.payout.request`, the same endpoint as a wallet payout; `requestPayout` ignores `adminNotes` and limits the amount to the regular wallet's `activeIncome` (or eligible `passiveIncome`), and Super Package commissions are not added to either field. Impact: a user whose balance comes only from Super Package commissions always gets "You are not eligible for payout", and a user who also has active income has the payout taken from active income while the screen says it is a Super Package commission withdrawal. Fix: add a server path that withdraws Super Package commissions and call it here, or remove this source until one exists.
- [LOW] L538 (CONFIRMED) The "Your sucessfull downline" tile prints "✗ Need ≥ 10" when `hasMinimumCoursePurchases` is false, but the server rule is `referralsWithCoursePurchases >= 7` and the passing text is "✓ ≥ 7". Impact: a user with fewer than 7 buying referrals is told the target is 10 instead of 7. Fix: change the failing text to "✗ Need ≥ 7", and show the separate rule of 10 direct referrals (`hasMinimumReferrals`) in its own tile.

- [HIGH] L266-278 (CONFIRMED) For `formData.rechargeType === 'postpaid'` `handlePayment` stops unless `formData.billDetails` has a bill reference, but `MobileRecharge.jsx` (the only postpaid entry point) never puts `billDetails` in the navigation state and there is no bill fetch screen. - [LOW] L562 (CONFIRMED) The details card labels `formData.mobileNumber` as "Mobile" (also "Mobile Number" in the confirm modal at L603), and L578 prints "Prepaid" for every type that is not postpaid. Impact: on a DTH recharge the subscriber ID is shown as a mobile number and the type is shown as "Prepaid".
