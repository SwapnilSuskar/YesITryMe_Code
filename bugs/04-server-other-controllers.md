# Server: shop, tasks, KYC and other controllers

Scanned: 13 files, 4016 lines. Found: 5 critical, 3 high, 15 medium, 7 low.

## server/controllers/productController.js

- [LOW] L353 (CONFIRMED) `getPublicProducts` calls `category.match(...)` on `req.query.category` without checking that it is a string (the same call is at L272 in `getProducts`). Impact: a request to the public route `GET /api/products/public?category=a&category=b` makes `category` an array, `match` is not a function, and the handler answers 500 instead of a product list. Fix: accept `category` only when `typeof category === "string"`, otherwise ignore it or return 400.
- [MEDIUM] L419-422 (CONFIRMED) `getProductById` is mounted as a public route (`router.get('/:id')` in `server/routes/products.js` sits before `protect`) but it has no `status: "active"` filter and it populates `createdBy` and `updatedBy` with the `email` field. Impact: anyone without a login who has a product id can read draft and inactive products, and every product response exposes the email address of the admin who created or updated it. Fix: in this public handler return 404 unless `product.status === "active"`, and remove `email` from the two `populate` calls (keep the full version for an admin-only route).
- [MEDIUM] L521-531 (CONFIRMED) In `updateProduct`, when the body contains `distributionEnabled` but not `distributionPercent`, `percent` is taken as `updateData.distributionPercent ?? 0`, which is 0, so `distributionEnabled` is forced to `false` and `distributionPercent` is overwritten with 0. Impact: an update that sends only `distributionEnabled: true` (for example a toggle) silently switches the reward pool off and erases the stored percentage, so confirmed orders for that product pay no shop reward or commission. Fix: when `distributionPercent` is absent from the request, load the product and use its stored `distributionPercent` for the check, and do not overwrite the stored percentage.

## server/controllers/productOrderController.js

- [MEDIUM] L70-83 (CONFIRMED) `sumPendingCoinsCommitted` counts `coinsApplied` of every order in status `awaiting_payment` or `payment_submitted`, and `createProductOrder` (L188-194) subtracts that sum from the spendable coins, but no code ever moves an unpaid order to `cancelled` and there is no user cancel route. Impact: a user who creates an order with a coin discount and never pays has those coins counted as reserved for ever, so every later shop order gets a smaller coin discount or none, until an admin deletes the old order. Fix: add a user cancel endpoint and expire `awaiting_payment` orders after a fixed time (set status `cancelled`), or ignore orders older than that time in `sumPendingCoinsCommitted`.
- [MEDIUM] L381-387 (CONFIRMED) `submitProductOrderPayment` uploads `req.files.paymentProof` to Cloudinary with `resource_type: "auto"` and never checks `file.mimetype` or the file content. Impact: any logged-in user can store arbitrary files of up to 10MB (HTML, SVG, video, archives) on the company Cloudinary account as a "payment proof", and the admin panel then links to that file. Fix: accept only `image/jpeg`, `image/png`, `image/webp` (and PDF if wanted), reject everything else with 400, and upload with `resource_type: "image"`.
- [CRITICAL] L487-535 (CONFIRMED) `adminVerifyProductOrder` reads the order, checks `order.status !== "payment_submitted"` in memory, then pays commissions with `distributeProductOrderWalletCommissions(order)` and only afterwards saves the new status; nothing claims the order atomically. Impact: when the verify request is sent twice (a double click, or two admins at once), both requests pass the status check and the `productCommissionsDistributed` check, so the buyer's shop reward and every upline commission are credited to the rupee wallets twice for one order; a verify and a reject that arrive together can also pay commission on an order that ends up rejected. Fix: claim the order first with one atomic update such as `ProductOrder.findOneAndUpdate({ _id: id, status: "payment_submitted" }, { status: "confirmed", verifiedAt, verifiedBy }, { new: true })`, stop when it returns null, and set the status back if a later step fails.
- [MEDIUM] L499-515 (LIKELY) `adminVerifyProductOrder` takes the coins from the coin wallet only at verification time, while `createProductOrder` merely counts them as reserved, so the coins stay in `CoinWallet.balance` and can be spent elsewhere (coin withdrawal, or two orders created at the same moment that both pass the spendable check at L187-194). Impact: the user pays the discounted amount by UPI, then `wallet.deductCoins` throws "Insufficient coins", the admin gets a 400 and the paid order can never be confirmed, only rejected or deleted. Fix: deduct the coins when the order is created and refund them with `refundProductOrderCoins` on reject, cancel or expiry.
- [HIGH] L507-533 (CONFIRMED) In `adminVerifyProductOrder` the coins are deducted and `order.coinsDeducted = true` is set only in memory (L507), and when `distributeProductOrderWalletCommissions` then throws, the handler returns at L527 without `order.save()`. Impact: the coins are gone from the wallet but the stored order still has `coinsDeducted: false` and status `payment_submitted`; every retry fails at L501 with "These coins were already applied for this order", and rejecting or deleting the order refunds nothing because `refundProductOrderCoins` exits when `coinsDeducted` is false, so the user loses the coins; for an order without coins, the retry pays again every wallet that was credited before the failure. Fix: save `coinsDeducted` right after the deduction, and make the commission distribution all-or-nothing (a MongoDB transaction, or record each credited wallet on the order and skip it on retry).
- [LOW] L611-613 (LIKELY) `adminDeleteProductOrder` calls `cloudinary.uploader.destroy(order.paymentProofPublicId, { resource_type: "auto" })`, but Cloudinary's destroy call accepts only `image`, `video` or `raw`, and the error is caught and only logged. Impact: the payment proof screenshot of a deleted order is never removed from Cloudinary. Fix: store the `resource_type` returned by the upload on the order and pass it to `destroy` (or use `"image"`).

## server/controllers/videoTasksController.js

- [MEDIUM] L532 (CONFIRMED) `claimVideoAction` decides that a video was watched from `watchTimeSeconds` in the request body. Impact: a user can post `{ action: "view", watchTimeSeconds: 30 }` for every video without playing any of them and collect the 50-coin view reward each time. Fix: record on the server when the user opened the video (for example a "start" record with a timestamp) and pay the view reward only when at least 30 seconds have passed since then.
- [MEDIUM] L549-566 (CONFIRMED) `claimVideoAction` creates the `VideoEngagement` record first and credits the coins with `wallet.addCoins` afterwards, with no rollback (`createVideoShareToken` does the same at L199-213). Impact: when `addCoins` fails (a database error or a wallet validation error), the user gets a 500 and no coins, and every retry is refused with "You have already claimed this action for this video", so the reward is lost for good. Fix: delete the engagement record when `addCoins` throws, or do both writes in one transaction.
- [LOW] L555 (CONFIRMED) `claimVideoAction` pays the comment reward without checking `commentText`; an empty or missing value is stored as an empty string. Impact: a user earns 30 coins per video for a comment with no text, and `listVideoComments` then hides that comment because it drops empty texts. Fix: for `action === "comment"` return 400 unless the trimmed `commentText` has a minimum length.

## server/controllers/kycController.js

- [LOW] L21-29 (CONFIRMED) `submitKyc` checks for an existing application with `Kyc.findOne` and creates the new one much later at L113, and the `Kyc` schema has no unique index on `userId`. Impact: two submit requests sent together (a double click) both pass the check and create two pending applications for one user, which an admin can then approve and reject separately. Fix: add a unique index on `userId` in the `Kyc` model, or create the record with an atomic upsert on `userId`.
- [MEDIUM] L44-46 (CONFIRMED) On resubmission `submitKyc` builds `publicId` from the last URL segment only, for example `USER1-aadhaar-1700000000000`, but the files were uploaded into the folder `kyc-documents`, so the real public id is `kyc-documents/USER1-aadhaar-1700000000000`. Impact: `cloudinary.v2.uploader.destroy` never finds the file, so the Aadhaar, PAN and bank document images of every rejected application stay on Cloudinary at their old public URLs after the database record is deleted. Fix: prefix the id with `kyc-documents/`, or store each `public_id` on the `Kyc` record at upload time and destroy by that value.
- [MEDIUM] L54 (CONFIRMED) `submitKyc` deletes the rejected `Kyc` record before the new files are compressed, uploaded and validated. Impact: when the resubmission then fails (a file is missing so the required `aadhaarUrl`, `panUrl` or `kycDocUrl` fails validation at L113, or `compressKycDocument` throws on a file that is not an image), the user gets a 500, the old application with the admin's rejection notes is already gone, `GET /api/kyc/status` answers "No KYC application found", and the documents uploaded in this attempt are left on Cloudinary with no record. Fix: check that all three files and the four text fields are present before touching anything, and delete the old record only after the new one is saved.
- [MEDIUM] L275-282 (LIKELY) `approveKyc` sets the user's `status` to `"kyc_verified"` without looking at the current value, and also writes `kycVerified: true`, a field that the `User` schema does not define, so Mongoose drops it. Impact: a user with status `blocked` whose application is still pending becomes `kyc_verified` on approval and is unblocked, and a `free` user who never bought a package gets a status that other code treats as an activated account (for example `canUserShare` in `videoTasksController.js`). Fix: change the status only when the current status is `active`, keep `blocked` and `free` unchanged, and store the KYC result in a field that exists in the schema.

## server/controllers/packageController.js

- [CRITICAL] L26-74 (CONFIRMED) `purchasePackage`, reachable by any logged-in user at `POST /api/packages/purchase`, calls `referralService.processPackagePurchase` with no payment check at all: no wallet debit, no payment verification record, no admin approval. Impact: a user who posts `{ "packageName": "<any active package>", "paymentMethod": "upi" }` receives an active purchase with `paymentStatus: "completed"`, their status becomes `active`, and the full commission for that package is credited to the rupee wallets of their sponsor chain and the admin wallet without any money coming in; a user can register accounts under their own referral code, call this route from each one, and withdraw the commission. Fix: remove this route, or restrict it to admins, so that a purchase is created only by the verified payment flow.

## server/controllers/servicesController.js

- [MEDIUM] L11-18 (CONFIRMED) `ensureDefaults` re-inserts every entry of `DEFAULT_CONFIGS` that is missing from the collection, and it runs on every call of `listActiveServiceConfigs` and `adminListServiceConfigs`. Impact: after an admin deletes one of the four default services (`insurance`, `credit_card`, `demat_account`, `bank_account`) through `adminDeleteServiceConfig`, the next list request creates it again as active with the default title, so these services cannot be deleted and the admin's edits to them are lost. Fix: seed the defaults once (only when the collection is empty, or in a setup step), or mark a deleted default as `isActive: false` instead of removing the document.
- [LOW] L73-93 (CONFIRMED) `adminUpsertServiceConfig` takes `serviceKey` from the URL and upserts with it, without the `/^[a-z0-9_]+$/` check that `adminCreateServiceConfig` applies. Impact: a `PUT /api/services/admin/configs/<key>` with a mistyped key or one with spaces or capitals does not fail but creates a new service under that key. ## server/controllers/notificationController.js

- [MEDIUM] L26-30 (CONFIRMED) `getNotificationStream` keeps one response per user in `global.notificationStreams` with `set(userId, res)`, and the `close` handler runs `delete(userId)` without checking that the stored response is its own. ## server/controllers/nomineeController.js

- [CRITICAL] L9-17 (CONFIRMED) `getNominee` reads the nominee of the `userId` in the URL and never compares it with `req.user.userId`; the route has only `protect`. Impact: any logged-in user can call `GET /api/nominee/<another userId>` and read that user's nominee name, relation, mobile number and address (user ids are shared as referral codes). Fix: use `req.user.userId` instead of the URL parameter, or return 403 unless the two are equal or `req.user.role === "admin"`.
- [CRITICAL] L26-51 (CONFIRMED) `createOrUpdateNominee` writes the nominee of the `userId` in the URL with no check against `req.user.userId`. Impact: any logged-in user can call `POST /api/nominee/<another userId>` and replace that user's nominee, the person entitled to the account's money, with their own details. Fix: use `req.user.userId`, or return 403 unless the URL id equals it or the caller is an admin.
- [MEDIUM] L46 (CONFIRMED) `createOrUpdateNominee` saves through `Nominee.createOrUpdate`, which updates the existing record but never sets `isActive` back to `true`, while `deleteNominee` only sets `isActive: false` and `getNominee` reads only active records. Impact: after a user deletes their nominee once, every new nominee they save answers "saved successfully" but `getNominee` returns `null`, so the nominee page stays empty for that user permanently. Fix: pass `isActive: true` in the data given to `Nominee.createOrUpdate`.
- [CRITICAL] L60-72 (CONFIRMED) `deleteNominee` deactivates the nominee of the `userId` in the URL with no check against `req.user.userId`. Impact: any logged-in user can call `DELETE /api/nominee/<another userId>` and remove that user's nominee. Fix: use `req.user.userId`, or return 403 unless the URL id equals it or the caller is an admin.
- [HIGH] L84-87 (LIKELY) `getAllNominees` is commented as admin only, but neither the handler nor its route (`router.get('/', protect, getAllNominees)`) checks the admin role, and it populates `userId`, which is a String such as the user code while `User._id` is an ObjectId. Impact: any logged-in user can call `GET /api/nominee` and receive every active nominee record (name, relation, mobile, address); depending on the Mongoose version the populate either throws a cast error (500 for admins too) or replaces `userId` with `null`, so the admin never sees which user a nominee belongs to. Fix: add the `admin` middleware to the route, and load the users with `User.find({ userId: { $in: ids } })` instead of `populate('userId')`.

## server/controllers/contactController.js

- [MEDIUM] L3-20 (CONFIRMED) `sendContactQuery` is public, has no rate limit, no captcha and no length limit on `name`, `email` or `message`, and each request sends one email through the company Gmail account. Impact: a simple script can post thousands of requests, flood the company inbox and use up the Gmail daily sending quota, which stops the other emails sent from the same account (for example OTP emails) until the quota resets. Fix: put a rate limiter on `POST /api/contact/send` (for example 5 per hour per IP) and cap the length of the three fields.
- [MEDIUM] L22-27 (CONFIRMED) `sendContactQuery` puts `name`, `email` and `message` from the request straight into the HTML body of the email without escaping. Impact: anyone can send the company inbox an email, from the company's own address, that contains arbitrary HTML such as a fake login form, misleading links or tracking images. Fix: escape `&`, `<`, `>` and quotes in the three values before building the HTML, or send the message as plain `text`.
