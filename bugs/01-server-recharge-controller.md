# Server: recharge controller

Scanned: 1 files, 3104 lines. Found: 6 critical, 1 high, 10 medium, 4 low.

## server/controllers/rechargeController.js

- [MEDIUM] L562 (LIKELY) `isA1TopupSuccessStatus` tests the status text with the unanchored regular expression `/success/i`, and `extractA1TopupStatus` (L548-559) falls back to the `message` field when `status` is empty, so any text that merely contains the word, such as "Unsuccessful" or "Recharge not successful", is treated as a successful recharge. Impact: a failed recharge whose provider text contains "success" is marked `success`, the user is not refunded, and admin commission and the 10% coin bonus are paid. Fix: compare the trimmed, lower-cased `status` field against an exact list of success values (for example `success`, `successful`) and never derive success from the free-text `message` field.
- [CRITICAL] L871-875 (CONFIRMED) `markRechargeSuccess` decides whether to pay by reading `recharge.commissionDistributed` from the in-memory document, and `grantRechargeCoinBonusIfNeeded` (L794-836) reads the coin wallet, checks for the reference `RECHARGE_BONUS_<id>` and then writes, so neither check is atomic, while the same pending recharge is polled at the same time by independent copies of the document from `initiateRecharge`, `checkRechargeStatus`, `getRechargeHistory`, `getAllRecharges` and the 30 second `refreshOldPendingRecharges` timer. Impact: when two of these pollers see the provider report success for the same recharge at about the same moment (for example the user's status or history request and the background timer, or two server instances each running the timer), each one runs `distributeCommissions` and the coin bonus, so the admin commission, the user commission and the 10% coin bonus are credited twice for one recharge. Fix: claim the transition atomically with `Recharge.findOneAndUpdate({ _id, status: { $in: [pending statuses] } }, { $set: { status: "success", ... } })` and pay commission and bonus only when that update returns a document, and guard the payouts with atomic claims on `commissionDistributed` and `rechargeBonusGranted` (`findOneAndUpdate` with the flag `false` in the filter).
- [CRITICAL] L961-964 (LIKELY) `applyProviderResponse` treats every provider response whose status text is neither `/success/` nor `/(pending|inprocess|processing)/` as a definite failure (`outcome: "error"`), which includes an empty body (parsed to `{}`), an HTML or proxy error page, a JSON array, an unparseable body and an unknown status word, and `initiateRecharge` refunds the wallet on that outcome (L2035-2058) when the follow-up status check is equally unclear (`tryResolveRechargeAfterVendorError` returns `null` at L670-672 or L693). Impact: when the provider accepts the recharge but answers with an empty or unrecognised response, or the request times out and the status API answers with an unrecognised text, the recharge is marked `failed` and the user is refunded although the mobile number was actually recharged, so the platform loses the full amount. Fix: treat only an explicit failure status (for example `failure`, `failed`, `refunded`) as an error, map every other or empty status to `pending`, and leave the recharge in `processing` without a refund until the provider gives an explicit final status.
- [CRITICAL] L1013-1015 (CONFIRMED) `pollPendingRechargeStatus` returns `outcome: "error"` when a later status poll reports that the provider failed the recharge, but none of its callers outside `initiateRecharge` act on it: `maybeRefreshRechargeStatus` (L1104) discards the result and `refreshOldPendingRecharges` (L1179-1187) discards it through `Promise.allSettled`, and nothing sets the recharge to `failed` or refunds the `RechargeWallet`. Impact: when the provider first answers "Pending" (so `initiateRecharge` returns success with the wallet already debited) and fails the recharge a minute later, the recharge stays in `processing` forever and the user never gets the debited `netAmount` back. Fix: add one shared function that, on a confirmed provider failure, atomically moves the recharge from a pending status to `failed` and credits the refund with the reference `RECHARGE_WALLET_REFUND_<id>` exactly once, and call it from every place that receives `outcome: "error"`.
- [CRITICAL] L1144-1148 (CONFIRMED) `tryPromoteRechargeUsingWallet` marks a recharge as `success` only because it is older than `RECHARGE_WALLET_PROMOTE_MIN_AGE_MS` (120 seconds) and the user's `RechargeWallet` contains the debit transaction `RECHARGE_WALLET_<id>` without a refund transaction, which says nothing about whether the provider performed the recharge, and `pollPendingRechargeStatus` calls it (L1024) whenever the status polls ended without a final answer, including when every status call threw a network error. Impact: any recharge that is still pending at the provider after two minutes, or whose status cannot be fetched because the provider or proxy is down, or that was debited but never sent because the server crashed before the API call, is recorded as successful, the admin commission and the 10% coin bonus are paid, a success receipt is emailed, and the user is never refunded even when the provider later fails the recharge. Fix: remove the wallet-evidence promotion and change status to `success` only on an explicit success from the provider, leaving unresolved recharges in `processing` for manual review.
- [MEDIUM] L1164-1173 (CONFIRMED) `refreshOldPendingRecharges` selects the 10 pending recharges with the oldest `updatedAt`, but a recharge whose status poll returns an error outcome or throws is never saved, so its `updatedAt` never changes and it is selected again on every run. Impact: once 10 recharges are stuck in a pending status (which the unhandled failure outcome at L1013 produces), every 30 second run polls the same 10 records and no newer pending recharge is ever refreshed by the background job. Fix: record a `lastStatusCheckAt` timestamp on every poll attempt and sort and filter by it, and move recharges with a final failure out of the pending statuses.
- [HIGH] L1591-1614 (CONFIRMED) `distributeCommissions` loads the admin `Wallet`, adds `recharge.adminCommission` to `balance`, `totalEarned` and `passiveIncome` in memory and calls `save()`, which writes absolute values, and the user wallet is updated the same way at L1629-1652. Impact: the single admin wallet receives a commission from every recharge and from other features, so when two credits are saved at overlapping times the later save overwrites the earlier one and a commission (or any other concurrent change to that wallet's balance) is silently lost. Fix: credit with one atomic `Wallet.updateOne({ userId }, { $inc: { balance, totalEarned, passiveIncome }, $push: { transactions } }, { upsert: true })`.
- [CRITICAL] L1990-2024 (CONFIRMED) `initiateRecharge` reads the `RechargeWallet`, checks `rechargeWallet.balance < netAmount`, subtracts in memory and calls `save()`, which writes the new balance as an absolute value with no condition on the old balance, and the refund at L2037-2057 is written the same way. Impact: a user with ₹500 who sends two or more `POST /initiate` requests for ₹500 at the same time passes the balance check in each request, each save writes balance 0, and every request is sent to the provider, so the user gets several real recharges while paying for one. Fix: debit with a single conditional update, `RechargeWallet.findOneAndUpdate({ userId, balance: { $gte: amount } }, { $inc: { balance: -amount, totalSpent: amount }, $push: { transactions } })`, fail the recharge when it returns null, and write the refund with `$inc` as well.
- [MEDIUM] L2024-2030 (CONFIRMED) In `initiateRecharge` the wallet debit is saved at L2024 before `recharge.save()` at L2030 and before the provider call, with no compensation if a later step throws, because the outer `catch` at L2095 only returns HTTP 500. Impact: if `recharge.save()` at L2030 or L2117 fails, or the process restarts between the debit and the provider call, the user's wallet stays debited for a recharge that was never sent and no refund is made. Fix: wrap the steps after the debit in a `try`/`catch` that refunds the wallet when the provider request was never issued, or perform the debit and the status change in one transaction.
- [MEDIUM] L2070 (CONFIRMED) `initiateRecharge` returns `rechargeResult.vendorResponse`, the raw parsed provider response, to the end user in the failure response. Impact: any user whose recharge fails receives the provider's internal reply, which can contain the platform's provider account balance, transaction identifiers and messages such as the server IP that is not whitelisted. Fix: remove `vendorResponse` from the response and return only `message` and `error`.
- [MEDIUM] L2421-2441 (LIKELY) In the `catch` block of `processRechargeWithA1Topup`, when the recovery itself throws (`recoveryErr`, for example because `recharge.save()` at L2415 fails validation after `markRechargeSuccess` assigned a `NaN` `providerBalance` or `providerCommission` from a non-numeric provider field at L913-925), execution falls through to `return { success: false, errorCode: "VENDOR_API_ERROR" }`. Impact: `initiateRecharge` refunds the wallet although the request outcome is unknown or the provider already reported success, so the user keeps both the recharge and the money. Fix: in the `recoveryErr` handler return `true` (leave the recharge in `processing`, no refund), and in `applyProviderResponse` pass `providerCommission` and `providerBalance` only when `Number.isFinite` and not negative.
- [LOW] L2478-2481 (CONFIRMED) `checkRechargeStatus` passes `req.params.rechargeId` to `Recharge.findOne({ _id: rechargeId })` without checking that it is a valid ObjectId, and `updateRecharge` (L3008) and `deleteRecharge` (L3073) do the same with `findById`. Impact: a malformed id such as `/status/abc` throws a `CastError` and the user gets HTTP 500 "Failed to check recharge status" instead of 404. Fix: return 404 when `mongoose.Types.ObjectId.isValid(rechargeId)` is false.
- [MEDIUM] L2506 (LIKELY) `checkRechargeStatus` returns the whole `Recharge` document to the user, and `getRechargeHistory` does the same at L2559, including `aiTopUpResponse`, `providerResponse`, `providerBalance`, `providerCommission`, `adminCommission` and `adminNotes`. Impact: every user can read the platform's provider account balance (stored at L865-867 whenever the provider reports it), the provider's raw replies, the admin's margin on each recharge and internal admin notes. Fix: select or map only the user-facing fields before sending the response.
- [LOW] L2524-2534 (CONFIRMED) `getRechargeHistory` uses `parseInt(page)` and `parseInt(limit)` from the query string with no bounds, and `getAllRecharges` does the same at L2819-2837. Impact: `page=0` produces a negative `skip` and `limit=abc` produces `NaN`, both of which make the query throw and return HTTP 500, `limit=0` returns every record and makes `Math.ceil(total / limit)` infinite, and a very large `limit` returns the full collection. Fix: clamp with `Math.max(parseInt(page, 10) || 1, 1)` and `Math.min(Math.max(parseInt(limit, 10) || 10, 1), 100)`.
- [MEDIUM] L2679-2684 (CONFIRMED) `transferRechargeBalance` puts `req.body.recipientUserId` straight into the query `User.findOne({ userId: recipientUserId })` without checking that it is a string, and calls `.replace` on `recipientMobile` without checking its type; the server has no input sanitising middleware. Impact: sending `recipientUserId` as an object such as `{ "$regex": "^A" }` or `{ "$ne": "x" }` matches an arbitrary user, the money is transferred to that user and the response at L2786-2790 returns that user's `userId`, `mobile` and name, so users can be enumerated for ₹0.01 each, and a non-string `recipientMobile` throws and returns HTTP 500. Fix: reject the request unless `recipientUserId` and `recipientMobile` are strings.
- [CRITICAL] L2714-2774 (CONFIRMED) `transferRechargeBalance` reads both wallets with `RechargeWallet.getOrCreateWallet` outside the session, checks `senderWallet.balance < normalizedAmount` on that stale copy, computes the new balances in memory and saves absolute values, so the MongoDB transaction protects only the two writes and not the balance check, and `Math.max(0, ...)` at L2737 hides the resulting negative value. Impact: a user with ₹1000 who sends two transfer requests of ₹1000 to two different recipients at the same time passes the check in both, both transactions commit one after the other, the sender ends at 0 and both recipients receive ₹1000, so ₹1000 is created from nothing, and a concurrent top-up or refund on either wallet is overwritten in the same way. Fix: inside the transaction debit with `RechargeWallet.findOneAndUpdate({ userId: senderId, balance: { $gte: amount } }, { $inc: { balance: -amount, totalTransferredOut: amount }, $push: { transactions } }, { session })`, abort when it returns null, and credit the recipient with `$inc` in the same session.
- [LOW] L2737-2760 (CONFIRMED) `transferRechargeBalance` adds and subtracts `normalizedAmount` on `balance`, `totalTransferredOut`, `totalTransferredIn` and `totalAdded` without rounding to two decimals, unlike the debit in `initiateRecharge`. - [MEDIUM] L2859 (CONFIRMED) `getAllRecharges` loads users with `User.find({ userId: { $in: userIds } })` with no field selection and attaches each full user document to the response at L2870; the `password` field in the `User` schema has no `select: false`. - [LOW] L3031-3034 (CONFIRMED) `updateRecharge` looks up a changed operator only in `POSTPAID_OPERATORS` or `PREPAID_OPERATORS` and never in `DTH_OPERATORS`. Impact: when an admin changes the operator of a DTH recharge (for example from "Tata Play" to "Dish TV"), `operatorInfo` is undefined, so `operator` is updated while `operatorCode` and `operatorApiCode` keep the old operator's values. - [MEDIUM] L3045-3049 (CONFIRMED) `updateRecharge` writes the whole request body into the record with `findByIdAndUpdate` and has no logic tied to status changes, and when `amount` or `operator` is sent it overwrites `userCommission` with the full rate from `calculateCommissions` (L3024) without checking `discountApplied` or `activeMemberSnapshot` and without updating `netAmount`. Impact: an admin who sets a stuck recharge to `failed` or `refunded` does not refund the user's `RechargeWallet`, an admin who sets it to `success` pays no commission or coin bonus, and editing the amount of a pending recharge of a non-member makes `distributeCommissions` pay that user a commission they are not entitled to when the recharge later succeeds. Fix: accept only an explicit list of editable fields, route status changes through the shared success and failure-with-refund functions, and recalculate commissions with the same membership and discount rules as `initiateRecharge`.
- [MEDIUM] L3082-3090 (CONFIRMED) `deleteRecharge` blocks deletion only when `commissionDistributed` is true and `status` is `success`, so a recharge in `payment_success` or `processing` (wallet already debited, result unknown) or a `success` recharge whose commission was not yet distributed can be deleted. Impact: deleting a recharge that is still in progress removes the only record of the debit, so the background poller can no longer resolve it and the user is neither refunded nor shown the recharge. Fix: allow deletion only for the statuses `pending`, `failed` and `cancelled` when no unrefunded `RECHARGE_WALLET_<id>` debit exists.
